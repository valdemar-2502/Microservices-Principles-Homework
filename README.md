
# Домашнее задание к занятию «Микросервисы: принципы» - Kadancev Vladimir

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.

## Задача 1: API Gateway 

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:
- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.

## Ответ:

API Gateway — это единая точка входа, которая скрывает внутреннее устройство системы от клиентов (веб, мобильное приложение, админка). На шлюзе удобно делать то, что нужно всем сервисам: аутентификацию, трассировку и логирование.

### Требования

1. Маршрутизация запросов к нужному сервису на основе конфигурации.
2. Проверка аутентификационной информации в запросах.
3. Терминация HTTPS.

Дополнительно по лекции: удобное логирование и мониторинг, настройка через конфигурацию, работа в контейнерах без внутреннего состояния (stateless).

### Сравнительная таблица

| Критерий | Nginx | HAProxy | Traefik | Envoy | **Kong** | Apache APISIX |
|---|---|---|---|---|---|---|
| Маршрутизация по конфигурации | Да | Да | Да | Да | Да | Да |
| Проверка аутентификации | Частично через внешний сервис (`auth_request`), JWT нативно только в платной версии | Частично JWT и ACL, настраивается вручную | Частично через внешний сервис (ForwardAuth) | Да фильтры JWT и ext_authz | Да готовые плагины: JWT, Key Auth, OAuth2, OIDC | Да готовые плагины: JWT, Key Auth, OIDC |
| Терминация HTTPS | Да | Да | Да | Да | Да | Да |
| Логи и метрики (мониторинг) | Частично логи есть, метрики через доп. модули | Частично статистика есть, нужна настройка | Да метрики Prometheus | Да очень подробные метрики и трассировка | Да плагины для Prometheus, логирования и трассировки | Да плагины для Prometheus, логирования и трассировки |
| Конфигурация как код (YAML, файлы) | Да файлы | Да файлы | Да файлы, метки контейнеров | Да но сложный формат | Да декларативный YAML | Да YAML |
| Изменение без остановки | Частично reload | Частично reload | Да | Да | Да через Admin API | Да через Admin API |
| Простота освоения | Да просто | Частично средне | Да просто | Нет сложно | Да средне-просто | Частично средне |
| Бесплатная версия | Да | Да | Да | Да | Да | Да |

### Выбор: **Kong**

**Почему Kong:**

1. **Закрывает все три требования без программирования.** Маршруты и HTTPS-сертификаты описываются в конфигурации, а проверка токенов (JWT, OAuth2, ключи) включается готовым плагином.
2. **Соответствует идее лекции про единую точку входа.** Аутентификация, логирование и трассировка делаются один раз на шлюзе, а не в каждом сервисе. Сервисы остаются простыми.
3. **Подходит под «12 факторов».** Настраивается декларативным файлом или переменными окружения, не хранит состояние в процессе (stateless), запускается в контейнере, поэтому легко масштабируется горизонтально.
4. **Есть мониторинг «из коробки».** Метрики для Prometheus и вывод логов подключаются плагинами, это закрывает требования «централизованный мониторинг» и «централизованный сбор логов».
5. **Работает с BFF.** Если для веб-приложения и мобильного приложения понадобятся отдельные серверные части (Backend for Frontend), Kong можно поставить перед ними.

**Когда выбрал бы другое:** Traefik, если система небольшая и целиком живёт в Kubernetes или Docker (проще настройка). Nginx, если нужен только прокси без сложной авторизации.

## Задача 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:
- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Обоснуйте свой выбор.

## Ответ:

Событийная модель снижает связность сервисов и упрощает расширение системы: сервис публикует событие, а кто хочет, тот подписывается. Но у неё есть цена: система сложнее, а к инфраструктуре предъявляются повышенные требования. Поэтому брокер должен быть **надёжным и по возможности простым в эксплуатации**.

Запросы «запрос-ответ» при этом по-прежнему идут через REST, а брокер нужен там, где важны события и асинхронность.

### Требования

1. Кластеризация для надёжности.
2. Хранение сообщений на диске при доставке.
3. Высокая скорость.
4. Разные форматы сообщений.
5. Разделение прав доступа к разным потокам сообщений.
6. Простота эксплуатации.

### Сравнительная таблица

| Критерий | **Apache Kafka** | RabbitMQ | ActiveMQ Artemis | NATS JetStream | Redis Streams |
|---|---|---|---|---|---|
| Кластеризация | Да репликация партиций между узлами | Да кластер + quorum-очереди | Да | Да | Частично Redis Cluster, репликация асинхронная |
| Хранение на диске | Да журнал на диске (основа Kafka) | Да для durable-очередей | Да | Да | Частично в памяти, диск через RDB/AOF |
| Скорость | Да очень высокая (сотни тысяч–миллионы сообщений в секунду) | Частично средняя (десятки тысяч в секунду) | Частично средняя | Да высокая | Да высокая |
| Форматы сообщений | Да любые (JSON, Avro, Protobuf), есть Schema Registry | Да любые | Да любые + разные протоколы | Да любые | Да строки и байты |
| Права доступа к потокам | Да ACL на уровне топиков | Да права по vhost и очередям | Да | Да аккаунты и права на subject | Частично ACL на команды и ключи |
| Простота эксплуатации | Частично средне (с режимом KRaft ZooKeeper не нужен) | Да просто, есть веб-панель | Частично средне | Да очень просто | Да просто |
| Повторное чтение сообщений | Да да | Нет после подтверждения сообщение удаляется | Нет | Да | Да |
| Метрики для мониторинга | Да JMX, Prometheus | Да Prometheus | Да | Да | Да |

### Выбор: **Apache Kafka**

**Почему Kafka:**

1. **Надёжность.** Сообщения пишутся на диск и копируются на несколько узлов. Если узел выйдет из строя, данные не пропадут. Это закрывает требования про кластер и хранение на диске.
2. **Скорость.** Kafka рассчитана на большие потоки данных, по пропускной способности она впереди RabbitMQ и ActiveMQ.
3. **Любые форматы.** Kafka передаёт просто байты, поэтому можно использовать JSON, Avro, Protobuf. Это соответствует принципу лекции про технологическую независимость: сервисы на разных языках могут обмениваться событиями. Для контроля структуры данных есть Schema Registry, что помогает соблюдать **обратную совместимость** контрактов.
4. **Права доступа.** ACL позволяют указать, какой сервис может писать в конкретный топик и какой читать. Каждый сервис видит только свои потоки, что соответствует требованию «безопасное поведение».
5. **Мониторинг.** Метрики доступны для Prometheus, топики и очереди легко наблюдать централизованно.
6. **Дополнительное преимущество.** Сообщения не удаляются сразу после прочтения, поэтому новый сервис может прочитать историю событий.

**Минусы и как их снизить:** Kafka сложнее RabbitMQ в настройке. В новых версиях (режим KRaft) отдельный ZooKeeper не нужен, а в Kubernetes кластер можно развернуть готовым оператором (например, Strimzi). По лекции событийная модель увеличивает общую сложность, поэтому использовать брокер стоит только там, где действительно нужны события и асинхронность, а остальное оставить на REST.

**Когда выбрал бы другое:** RabbitMQ, если нагрузка небольшая, а команде важнее простота и гибкая маршрутизация сообщений.

## Задача 3: API Gateway * (необязательная)

### Есть три сервиса:

**minio**
- хранит загруженные файлы в бакете images,
- S3 протокол,

**uploader**
- принимает файл, если картинка сжимает и загружает его в minio,
- POST /v1/upload,

**security**
- регистрация пользователя POST /v1/user,
- получение информации о пользователе GET /v1/user,
- логин пользователя POST /v1/token,
- проверка токена GET /v1/token/validation.

### Необходимо воспользоваться любым балансировщиком и сделать API Gateway:

**POST /v1/register**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/user.

**POST /v1/token**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/token.

**GET /v1/user**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис security GET /v1/user.

**POST /v1/upload**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис uploader POST /v1/upload.

**GET /v1/user/{image}**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис minio GET /images/{image}.

### Ожидаемый результат

Результатом выполнения задачи должен быть docker compose файл, запустив который можно локально выполнить следующие команды с успешным результатом.
Предполагается, что для реализации API Gateway будет написан конфиг для NGinx или другого балансировщика нагрузки, который будет запущен как сервис через docker-compose и будет обеспечивать балансировку и проверку аутентификации входящих запросов.
Авторизация
curl -X POST -H 'Content-Type: application/json' -d '{"login":"bob", "password":"qwe123"}' http://localhost/token

**Загрузка файла**

curl -X POST -H 'Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJib2IifQ.hiMVLmssoTsy1MqbmIoviDeFPvo-nCd92d4UFiN2O2I' -H 'Content-Type: octet/stream' --data-binary @yourfilename.jpg http://localhost/upload

**Получение файла**
curl -X GET http://localhost/images/4e6df220-295e-4231-82bc-45e4b1484430.jpg
